- `worktree_lifecycle.py --recover` now brings an archived worktree back exactly as it was archived, including its uncommitted edits. Archiving keeps the worktree's git registration (and with it the worktree's own index), so recovery moves the archived directory back under that registration: staged and unstaged changes, intent-to-add and skip-worktree entries, file modes and untracked files all return unchanged. Across filesystems the directory is copied rather than moved, and nothing is deleted until the placed tree has been verified. If the branch was deleted in the meantime, the worktree comes back detached at its recorded commit with its index intact; if git has since collected that commit, recovery says so and exits with status 2. An archive whose path was archived again later is refused, instead of being placed under the newer archive's registration. Only when the registration is gone does recovery rebuild the checkout and reapply the patches saved at archive time; if git cannot be asked whether the registration still fits, recovery stops without changing anything rather than rebuilding. The reaper now saves those patches as two raw patches, staged and unstaged, generated with commands that ignore user diff settings and applied with options that ignore user apply settings, and records which patches it expected to write, so a patch that failed to save is reported as missing instead of treated as "nothing to restore". In that fallback, a conflict or a missing patch leaves the archive in place, prints retry commands that can be re-run safely, and `--recover` exits with status 2 instead of 0; so does a recovery onto a branch that has moved since archiving, or one git no longer recognises as a worktree. A plain trash directory is deleted only after the recovered tree is checked to match it byte for byte, including executable bits, nested repositories and files named like the reaper's own. Separately, a worktree whose branch has no commits of its own is no longer archived on the short 7-day "merged" clock while it holds uncommitted work: such a branch has merged nothing and had only passed the merge test vacuously. It now waits the 14-day unmerged window and shows as at-risk meanwhile. A clean one still drains at 7 days.
