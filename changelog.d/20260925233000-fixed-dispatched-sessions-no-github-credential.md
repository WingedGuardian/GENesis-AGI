- **A background session allowed to run `gh` no longer inherits the operator's GitHub credential.** The sealed configuration directory that keeps such a session from reconfiguring `gh` into running arbitrary commands copied the credential file into itself, because that is the only place `gh` looks for a token. The argument for the copy was that it lands owner-only inside an owner-only directory and so widens nobody's read access, which is true and answered the wrong question: it handed a session whose stated job is reading external pull requests a token carrying whatever scopes the operator's own login carries — on the install where this was measured, including the ability to delete repositories. The copy is gone, the directory is now synthesised from a constant, and such a session launches unauthenticated; verified by execution, against a control that authenticates. Installs that already ran the old code heal themselves with no migration step, because the file left the desired set and the existing stale sweep unlinks it on the next launch — verified on a live seal, which went from two files to one. Separately, `GH_TOKEN` is pinned to the empty string for every dispatched session rather than only allowlisted ones, since `gh` resolves that variable ahead of the configuration file (measured: a bogus value returns 401 against a perfectly good one), so an inherited token would otherwise outrank the credential-free directory; an empty value reads as unset, which neutralises without inventing. The pin is enforced rather than merely set — the launch path recomputes it and refuses any other value, which also means there is no way to supply a credential through an environment override.
- **Two limits stated rather than left to be discovered, because the obvious reading of the change is wrong.** An empty `GH_TOKEN` does **not** by itself de-authenticate a session: measured, `gh` falls back to the configuration file on disk and authenticates normally, and the variable that actually decides the question is `GH_CONFIG_DIR` — which is pinned only on the allowlisted path. So a dispatched session that is permitted a shell without declaring an allowlist still reaches the credential on disk, and pinning that variable more widely was tried and rejected: keying it on session origin reads tight but covers six dispatch profiles and every non-owner-attended conversation channel, and it would additionally point a process-global data directory at a read-only tree for all of them; pointing it at the sealed directory is a fail-open on precisely the installs that need it, since a rebuild that fails before its sweep leaves the old copied credential in place. The remedy for that surface is denying the shell on the one path that processes external content, not an environment pin — a shell can read the file whatever the variable says. And the profile that carries the `gh` grant has a prompt asking for authenticated writes that can no longer succeed and no path to grant it one; that profile has never run, and giving it a credential deliberately is separate work.
