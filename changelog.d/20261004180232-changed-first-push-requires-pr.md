- The push guard now refuses to create a branch on your configured public repository unless the same command opens its pull request — `git push -u origin HEAD && gh pr create --title "..." --body-file <file>` (a ready PR, not a draft). The pull request command must be one `gh` accepts without a terminal: a title and a body (an existing `--body-file`, or `--body`), or one of `--fill`, `--fill-first`, `--fill-verbose`. Labels, assignees, reviewers, milestones and projects are refused in it, because `gh` fails the whole create on a name it cannot resolve after the push has already run — add them afterwards with `gh pr edit`. A `branch.<name>.gh-merge-base` setting that points the PR anywhere but the default branch is refused too. Every other way of spelling a push to the public repository — another branch, a `src:dst` refspec, several branches, `--all`, a push from the default branch's checkout, a remote configured with `mirror = true` — is refused when it would create a branch there, or when the guard cannot tell which branches it would push; options that change neither the branches nor the destination (`--no-verify`, `--signed`, `git -c core.sshCommand=…`) do not count as "cannot tell", so a re-push carrying them is unaffected, as is a re-push of branches already published, a tag, a deletion or a dry run. A push from a directory the guard cannot resolve (`cd "$DIR" && git push …`) is refused unless it names another repository by URL; run it from the checkout or with `git -C <path>`. Work that is not ready for review stays committed locally. What remains: the pull request command can still fail when it runs (authentication, network), leaving the branch public with no PR; the next push of that branch is then refused until its PR is opened. With `hooks.asks.push_publish: off`, the chained form is the one the first-push prompt is silenced for; pushes to any other repository, and installs with no public repository declared, behave as before.
