- **`--next-for-validation` no longer re-picks a stuck `not-yet-done` row every pass.** `record_attempt` now sets `pr_verifications.nyd_repeat` on a `not-yet-done` attempt: 1 when the previous attempt was also `not-yet-done`, was finished (its tracking complete), and both evidence documents name the same remaining steps (their `not_yet_done` gaps, compared by `command` and `detail` with whitespace collapsed and case folded), else 0; any other verdict clears it. When the previous record had the same steps but its tracking was still pending, the write is that attempt re-recorded after routing, so the previous value is carried unchanged and the writers report it as a routing update rather than a new attempt. A fresh `not-yet-done` row still goes first with no wait. Only a row whose latest attempt repeated the one before it waits the re-attempt window (7 days, compared as parsed instants against `last_attempt_at`) and then returns to the front. The CLI says which happened and when the row is offered again, and the MCP writer's result carries `nyd_repeat` and `nyd_basis`. Before, a row whose remaining step needed a push, deploy or merge, which a standing validator may not do, held every pass, and the rest of the open ledger was never reached. A new additive migration adds the nullable column; until it runs, the picker applies no wait.
