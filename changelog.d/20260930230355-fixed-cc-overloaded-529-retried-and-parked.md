- **A Claude Code call that fails because the provider is overloaded (HTTP 529) is now retried instead of just failing.** Ego cycles, the ego's reconcile and realist checks, and inbox evaluations wait and re-run the same already-approved call up to three times (after 30s, 2m and 5m) before giving up; the approval prompt is never shown again for a retry. A call that had already done work before the overload (more than one turn) is not re-run, so its tool actions are not repeated; an overload that comes from an MCP tool rather than the provider is not re-run either. An inbox item whose overload outlasts the retries stays retriable instead of using up one of its attempts. An overload is now recognised as a capacity limit everywhere else too: a direct session parks for automatic resume, a conversation takes the same failover path as a rate limit, Telegram says the provider is overloaded, and the `cc.invocation_failed` event is a warning rather than an error. Separately, rate-limit and overload detection no longer match numbers that merely contain `429` or `529` (token counts, durations, timestamps, request and session ids), and the CLI's "temporarily limiting requests (not your usage limit)" message is treated as a short rate limit rather than an hours-long usage-limit lockout.
