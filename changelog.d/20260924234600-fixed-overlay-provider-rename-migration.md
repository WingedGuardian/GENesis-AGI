- **A renamed routing provider no longer breaks your local overlay on upgrade.** If you keep a `model_routing.local.yaml`, an override naming a provider that was renamed upstream used to fail in one of two ways: a partial provider override left an entry with no type or model and took the whole router down — Genesis still started, but every LLM call site was dark behind a single log line — while a call-site chain pinned to the old name was quietly discarded and the shipped chain ran in its place. Legacy names are now migrated automatically wherever the overlay is read, including the dashboard's save path, so an override survives the rename that caused it and the file is brought up to date the next time you save from the dashboard. If the overlay names both an old and a new key, the new one wins; if a chain names both, it collapses to one entry rather than routing to the same provider twice. Renames applied across two upgrades are followed through to the current name. A provider entry that is unusable after migration — missing its type or model, or left as an empty or malformed key by a half-finished edit — is skipped with a warning and reported as disabled, instead of taking routing offline.
