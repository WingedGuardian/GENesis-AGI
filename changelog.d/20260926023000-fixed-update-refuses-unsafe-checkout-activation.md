- **`update.sh` now refuses to deploy a checkout it cannot safely deploy, before it stops a service or clears a file.** It reported a successful update while the tree sat on a feature branch — force-discarding tracked ephemeral files on the way — and its refusal to run from a linked worktree was a path-substring test, so a worktree created anywhere other than the two directories it named was not recognised as one and went straight through. The checkout is now validated by git's own question (`--git-dir` against `--git-common-dir`) before the lock, before services stop, and before any tracked file is cleared, so an operator on the wrong branch gets a refusal naming that branch instead of a success row describing a deploy that did not happen. `GENESIS_ALLOW_NON_DEPLOY_BRANCH=1` is the deliberate override.
- **A success row can no longer claim a deploy that never restarted the server.** `update.sh` wrote `status='success'` into `update_history` from three places and only one of them could record that the server was left down, so the other two produced a row naming the new HEAD while nothing was serving it. All three now carry the `genesis-server-not-restarted` marker when that is what happened. On the no-change path, which has no health check, that is decided by the service's state after the restart attempt rather than by whether it was running beforehand — a restart that never came back used to count as done. And with the server down, that path no longer writes a success row over a `failed` or `rolled_back` one, which is the record the next update's recovery step reads to know it must restart the server.
- **The deploy target is resolved from the remote that will actually be fetched.** The branch comes from a persisted `github.deploy_branch` override, then the live remote's advertised HEAD, then the cached remote-tracking HEAD, then `main` — and both fetch refspecs are fully qualified, so a tag sharing the branch's name cannot win git's disambiguation and leave a stale commit activated. Only the private deploy ref is fatal to fetch: the remote-tracking ref is refreshed separately, because a stale ancestor blocking its own descendant after a branch rename said nothing about whether the deploy head arrived and used to fail every update until someone pruned by hand. `update.sh` is the only reader of the override for now — the dashboard update check and the version collector still compare against a hard-coded `main` branch, so pointing the override at a non-default branch makes those two describe a branch the deploy does not target.
- **A config that exists but cannot be read now stops the update instead of being guessed around.** Reading `github.deploy_branch` without PyYAML used to fall back to a hand-written parser that returned a branch name — a guess from the very path whose premise is that the file cannot be read. Treating an unreadable file as "no override" is no better: when the checkout happens to be on the remote's default branch, the update deploys that instead of the branch the operator configured. So an absent file or key reads as empty, and a file that exists but cannot be parsed refuses, for both `deploy_branch` and `public_repo`. Config is read through the virtualenv's Python first, where PyYAML is a dependency, as it was before this change.
