- **The deploy-health report now says what the live-move repair saved, and where.** After the repair puts a half-written `live` checkout back to its rollback tag, each of its reports is listed with its time, its backup folder and how many paths the update did not write were saved there (`live_repair_saved:<n>`), until you run `scripts/deploy_candidates repair-move --dismiss <time>`. Putting them back will be `repair-move --restore <time>`, which comes in a later release; until then the saved copies are in the named folder. Backups are pruned 90 days after the last write to their folder. Only the newest eight reports are read; older ones are counted as informational. A report the reader cannot read safely (a name, file type, size, row count or checkout the repair never writes) is counted as refused and named in the server log, and never blanks the rest of the report. An interrupted repair reads as unresolved only while the shared restart guard still calls the checkout half-written. The host guardian's diagnosis picks the newest eligible report inside the container, for this checkout only, by the time in its folder name, so newer dismissed or superseded reports cannot hide it. The open health endpoint shows only the counts to a caller without credentials.
